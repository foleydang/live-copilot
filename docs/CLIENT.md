# 客户端选型：H5 / 微信小程序 / 原生 App

## 结论先说

**现阶段（POC → 前 3 个客户）保留 H5，商业化后再考虑小程序"控制端"。**

助播台是**单台闲置手机常亮**的专用设备，不是 C 端分发产品；H5 在这个场景下是最优解。小程序的核心价值（扫码即用、用户增长、支付闭环）在这里几乎用不上，反而引入审核、资质、类目限制、音频后台限制等一堆包袱。

## 为什么 H5 现在更好

| 维度 | H5 | 小程序 |
|---|---|---|
| 部署 | 改完代码即生效，无审核 | 需要企业主体 + 类目审核（工具/商业服务）1~7 天 |
| 更新 | 客户端无需任何操作 | 版本审核 + 强制升级策略 |
| 音频自动播放 | 用户点一次"开始助播"即可解锁 | `innerAudioContext` 也要解锁一次，差不多 |
| 屏幕常亮 | `navigator.wakeLock`（Chrome/Android）+ `<meta>` | `wx.setKeepScreenOn`（全平台可用）✅ 小程序更稳 |
| 后台音频 | iOS 锁屏即停，安卓看浏览器 | **也停** —— 小程序后台音频需 `backgroundAudioManager` + 音乐类目 |
| WebSocket | 全平台支持 | 全平台支持，但强制 wss + 域名白名单 |
| 分享 | URL 带 token 即可 | 小程序码 / 分享卡片 |
| 资质 | 无需 | 企业主体 + 类目（直播相关更严） |
| 成本 | 0 | 企业主体 300 元/年认证 + 开发工时 |
| 调试 | Chrome DevTools | 微信开发者工具 + 真机预览 |

**真正的"痛点"**（iOS 锁屏断音）小程序**解决不了**：`backgroundAudioManager` 只允许音乐类账号申请，直播助播拿不到这个类目。

## 什么时候该上小程序

当满足以下任一条件时再考虑：

1. **客户增长到 10+ 家**，需要店主在手机上"管理"而不只是"用" → 小程序适合做**控制端**（配置 / 静音 / 看板 / 开播），音频播放仍留在常亮设备的 H5
2. **需要微信扫码分享客户配置页**（"扫这个码就能开你的助播台"）
3. **需要微信支付闭环**（客户在小程序里续费，而不是转账）

## 如果要做小程序，怎么做

建议拆成**两套产品**：

```
┌─────────────────────┐        ┌──────────────────────┐
│  H5 助播台（现有）    │        │  小程序"控制端"（新增） │
│  - 常亮设备专用       │        │  - 店主手机用           │
│  - 播放音频          │        │  - 配置 / 静音 / 看板   │
│  - 显示提词          │        │  - 不播音频（不抢声卡）  │
│  - 扫码即用，无审核   │        │  - 审核 / 类目 / 资质    │
└──────────┬──────────┘        └──────────┬───────────┘
           │                              │
           │    共用后端 API /api/...      │
           └────────────┬─────────────────┘
                        ▼
              live-copilot 服务（已有）
```

小程序只需要调用已有的 `/api/kb`、`/api/stats`、`/api/mute`、`/api/usage`，**不需要重写后端**。前端用 Taro / uni-app 或原生小程序都能做，工期 1~2 周。

## 现在立刻能让 H5 更接近小程序体验的优化

不用等小程序，先把这几件低成本的事做了：

1. ✅ **PWA manifest**：`static/manifest.webmanifest` + `<link rel="manifest">`，让店主"添加到主屏幕"后全屏、无地址栏
2. ✅ **`<meta name="apple-mobile-web-app-capable">`**：已经做了
3. ⏳ **二维码带 token**：让店主扫一次就能开，不用手输 URL（后端已经支持 `?t=`）
4. ⏳ **nginx + HTTPS + 域名**：小程序硬性要求，现在不做也行；等要做小程序时再配
